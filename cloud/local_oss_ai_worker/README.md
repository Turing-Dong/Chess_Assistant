# Local OSS AI Worker

This worker runs on a second computer. It replaces the Aliyun FC handler during
development:

1. ESP32 uploads `devices/<device_id>/requests/<frame_id>.jpg`.
2. ESP32 uploads `devices/<device_id>/requests/latest.json`.
3. This worker polls `latest.json`, downloads the image, and calls
   `process_image`.
4. The worker writes a compact device result to
   `devices/<device_id>/results/<frame_id>.json` and keeps the full diagnostic
   result in the configured local debug directory.
5. ESP32 keeps its existing result polling flow.

The worker recognizes the board with OpenCV and vision AI, then can pass a
validated position to a Xiangqi UCI engine. If no engine is configured, the
worker keeps the validated AI move and reports `engine_status=not_configured`.

Candidate pieces are classified locally first with the fine-tuned 14-class
PP-LCNet model. Predictions below the configured confidence or score-margin
threshold automatically use the existing cloud candidate classifier as a
fallback. The main vision and move-decision stages remain unchanged.

Device IDs are generated by firmware from each board's full Wi-Fi STA MAC as
`chess-XXXXXXXXXXXX`. They are stable per board, so users do not need to look
up MAC addresses manually.

## Install

Use a RAM user or temporary STS credentials with read/write permission for the
target OSS bucket. Do not commit secrets to this repository.

```powershell
cd cloud/local_oss_ai_worker
python -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -r requirements.txt
```

The default local model directory is:

```text
../local_piece_classifier/output/xiangqi_pplcnet_x1_0_finetune/inference
```

It must contain `inference.json` and `inference.pdiparams`. Override the path
with `CHESS_LOCAL_CLASSIFIER_MODEL_DIR` when the worker and model are deployed
to different directories.

With `CHESS_LOCAL_CLASSIFIER_BACKEND=auto`, the worker uses Paddle directly if
it is installed in the worker environment. Otherwise it starts one persistent
inference process with `../local_piece_classifier/.venv/Scripts/python.exe`, so
the model is loaded once and the worker's lightweight environment stays
independent. Set `CHESS_LOCAL_CLASSIFIER_PYTHON` when that environment is in a
different location.

Set credentials in the second computer's shell:

```powershell
$env:ALIYUN_ACCESS_KEY_ID="your-access-key-id"
$env:ALIYUN_ACCESS_KEY_SECRET="your-access-key-secret"
# Optional when using STS:
# $env:ALIYUN_SECURITY_TOKEN="your-security-token"
```

Set the AI service key as a separate local environment variable. Do not write it
into source files or commit it to git:

```powershell
$env:CHESS_AI_API_KEY="your-ai-api-key"
$env:CHESS_AI_PROVIDER="qwen"
$env:CHESS_AI_MODEL="qwen3-vl-plus"
```

## Xiangqi Engine

The worker uses the UCI-compatible Fairy-Stockfish Xiangqi variant when
`CHESS_ENGINE_PATH` points to its executable. Download a suitable Windows or
Linux binary separately, then configure:

```text
CHESS_ENGINE_ENABLED=true
CHESS_ENGINE_PATH=C:\\tools\\fairy-stockfish.exe
CHESS_ENGINE_MOVETIME_MS=1500
CHESS_ENGINE_TIMEOUT_MS=20000
# Fairy-Stockfish Xiangqi UCI moves use ranks 1-10 by default.
# CHESS_ENGINE_COORDINATE_BASE=1
```

The worker converts the recognized pieces to Xiangqi FEN, analyzes both logical
sides (`shuai` and `jiang`) independently, and writes engine moves to
`engine_recommended_moves`. When engine analysis succeeds, those moves replace
`recommended_moves`; the original AI result remains in the debug JSON.

Set `CHESS_ENGINE_COORDINATE_BASE=0` for an engine that emits Xiangqi ranks
`0-9` instead of Fairy-Stockfish's `1-10` format.

`CHESS_AI_CURL_FALLBACK=true` enables a native `curl` fallback when Python's
HTTPS stack fails before receiving an AI response; it is enabled by default.

Use `CHESS_AI_PROVIDER=qwen` for Alibaba Cloud Model Studio / DashScope
OpenAI-compatible chat completions. Use `CHESS_AI_PROVIDER=openai` for OpenAI
Responses API. The worker also accepts `OPENAI_API_KEY` if you prefer that
variable name for OpenAI.

Alternatively, create a local `.env` file next to `worker.py`. The real `.env`
file is ignored by git:

```powershell
Copy-Item .env.example .env
notepad .env
```

## Run

On Windows, double-click `run_worker.bat`. On the first run it creates `.env`
from `.env.example`; fill in `OSS_BUCKET`, `DEVICE_IDS`, and credentials, then
run the bat again.

For one device:

```powershell
python worker.py `
  --bucket esp32-chess-assistant `
  --device-id chess-AABBCCDDEEFF `
  --region cn-hangzhou `
  --debug-dir debug
```

For multiple known devices:

```powershell
python worker.py `
  --bucket esp32-chess-assistant `
  --device-ids chess-AABBCCDDEEFF,chess-112233445566 `
  --region cn-hangzhou `
  --debug-dir debug
```

In `.env`, use either the old single-device setting:

```text
DEVICE_ID=chess-AABBCCDDEEFF
```

or the multi-device setting:

```text
DEVICE_IDS=chess-AABBCCDDEEFF,chess-112233445566,chess-778899AABBCC
```

If you want the worker to scan OSS for existing
`devices/<device_id>/requests/latest.json` objects, enable discovery:

```text
DISCOVER_DEVICES=true
```

The worker loads `.env` by default. To use another path:

```powershell
python worker.py --bucket esp32-chess-assistant --device-ids chess-AABBCCDDEEFF,chess-112233445566 --env-file C:\secure\chess-worker.env
```

If you prefer a different environment variable name for the AI key:

```powershell
python worker.py --bucket esp32-chess-assistant --device-ids chess-AABBCCDDEEFF,chess-112233445566 --ai-api-key-env MY_AI_KEY
```

For one-shot testing:

```powershell
python worker.py --bucket esp32-chess-assistant --device-ids chess-AABBCCDDEEFF,chess-112233445566 --once
```

## OpenCV Geometry

The OpenCV path now uses two separate geometry stages:

```text
source image -> validate and center-crop to 1080x1080
-> detect broad board quad -> rectify with enough surrounding board area
-> detect the playable 9x10 grid crop in the rectified image
-> detect circles on both the rectified color image and a grid-suppressed copy
-> fuse candidates -> pre-snap centers to board points -> build original-color crops
-> recognize pieces -> validate the finalized position -> ask AI for moves
```

The rectification frame is intentionally broad so edge labels and border pieces are
kept. The board coordinate frame is detected later from the rectified grid lines.
If grid crop detection fails, the worker falls back to `CHESS_BOARD_CROP`.
The first vertical grid line is anchored relative to the left edge of the 1080x1080
crop, with a bounded dynamic search window. The upload manifest dimensions remain
unchanged in the result protocol so the ESP32 can validate and display the response.

Useful tuning variables:

- `CHESS_OPENCV_DETECT_GRID_CROP=true`
- `CHESS_CENTER_CROP_JPEG_QUALITY` (default `95`)
- `CHESS_GRID_ANCHOR_LEFT_REFERENCE=true`
- `CHESS_GRID_LEFT_REFERENCE_RATIO` (default `0.117`)
- `CHESS_GRID_LEFT_REFERENCE_SEARCH_IMAGE_RATIO` (default `0.03`)
- `CHESS_GRID_LEFT_REFERENCE_SEARCH_SPACING_RATIO` (default `0.25`)
- `CHESS_GRID_LEFT_REFERENCE_MIN_WEIGHT_RATIO` (default `0.50`)
- `CHESS_OPENCV_DUAL_CIRCLE_DETECTION=true`
- `CHESS_CIRCLE_FUSION_MIN_RADIUS_RATIO` (default `0.60`)
- `CHESS_CIRCLE_FUSION_MAX_DISTANCE_RATIO` (default `0.65`)
- `CHESS_CIRCLE_MAX_DARK_REGION_NARROW_RING_COVERAGE` (default `0.67`)
- `CHESS_CIRCLE_SINGLE_SOURCE_MAX_GRID_OFFSET` (default `0.40`)
- `CHESS_CANDIDATE_GRID_SNAP_MAX_OFFSET` (default `0.44`)
- `CHESS_GRID_ROI_HOUGH_FUSION=true`
- `CHESS_GRID_ROI_EXPECTED_RADIUS_RATIO` (default `0.445`)
- `CHESS_GRID_ROI_HOUGH_MAX_DISTANCE_RATIO` (default `0.45`)
- `CHESS_GRID_ROI_MAX_RADIUS_RATIO` (default `1.30`)
- `CHESS_GRID_ROI_FUSION_ROI_WEIGHT` / `CHESS_GRID_ROI_FUSION_HOUGH_WEIGHT`
  (defaults `0.65` / `0.35`)
- `CHESS_GRID_ROI_FUSION_THRESHOLD` (default `0.46`)
- `CHESS_ORIENTATION_DETECTION=true` infers the bottom side from red/black
  character-color distribution before canonical candidate coordinates are assigned
- `CHESS_ORIENTATION_MIN_COLOR_SAMPLES` (default `4`)
- `CHESS_ORIENTATION_MIN_SCORE` (default `0.12`)
- `CHESS_ORIENTATION_ROTATE_BOTTOM_SIDE_CROPS=true` rotates bottom-side piece
  crops by 180 degrees before character classification
- `CHESS_CHARACTER_COLOR_CONFLICT_MIN_MARGIN` (default `0.35`) rejects a
  side-specific OCR character instead of letting it overwrite conflicting
  pixel-based red/black evidence
- `CHESS_AI_SEPARATE_MOVE_DECISION=false` avoids a redundant cloud move call
  when Fairy-Stockfish is enabled (set it to `true` only when AI moves are needed)
- `CHESS_AI_ENABLE_REVIEW=true` keeps second-stage review available
- `CHESS_AI_REVIEW_MODE=auto` reviews only structurally invalid, low-confidence,
  incomplete, or repaired recognition results; use `always` for the legacy behavior
- `CHESS_AI_REVIEW_MIN_CONFIDENCE` (default `0.85`)
- `CHESS_AI_REVIEW_MIN_ORIENTATION_CONFIDENCE` (default `0.35`)
- `CHESS_AI_MIN_CANDIDATE_COVERAGE` (default `0.85`)
- `CHESS_RECTIFIED_BOARD_MARGIN_X` (default `0.07`)
- `CHESS_RECTIFIED_BOARD_MARGIN_TOP` (default `0.12`)
- `CHESS_RECTIFIED_BOARD_MARGIN_BOTTOM` (default `0.12`)
- `CHESS_GRID_CROP_HOUGH_MIN_LINE`
- `CHESS_GRID_CROP_HOUGH_MAX_GAP`
- `CHESS_GRID_CROP_HOUGH_THRESHOLD`
- `CHESS_GRID_CROP_MIN_WIDTH_RATIO` / `CHESS_GRID_CROP_MIN_HEIGHT_RATIO`
  (defaults `0.45` / `0.55`; lower the width ratio for an unrectified landscape frame)
- `CHESS_CIRCLE_CROP_EDGE_MARGIN_RATIO`
- `CHESS_LOCAL_CLASSIFIER_ENABLED=true`
- `CHESS_LOCAL_CLASSIFIER_MODEL_DIR` (defaults to the fine-tuned model above)
- `CHESS_LOCAL_CLASSIFIER_DEVICE=cpu` (`gpu` is also supported by a compatible
  Paddle installation)
- `CHESS_LOCAL_CLASSIFIER_BACKEND=auto` (`inprocess` or `subprocess` can force a
  backend)
- `CHESS_LOCAL_CLASSIFIER_PYTHON` (Python executable used by subprocess mode)
- `CHESS_LOCAL_CLASSIFIER_MIN_CONFIDENCE` (default `0.50`)
- `CHESS_LOCAL_CLASSIFIER_MIN_MARGIN` (default `0.10`)
- `CHESS_LOCAL_CLASSIFIER_CROP_SCALE` (default `1.35`, matching training crops)
- `CHESS_LOCAL_CLASSIFIER_CLOUD_FALLBACK=true`

## AI Integration Point

The implemented pipeline is:

```text
OpenAI vision -> structured move points
or later:
decode JPEG -> locate/rectify Xiangqi board -> detect pieces -> build board/FEN
-> run Xiangqi engine -> return player-local points
```

Keep these result fields stable because ESP32 currently validates them:

- `protocol_version`
- `device_id`
- `session_id`
- `frame_id`
- `sequence`
- `status`
- `image_width`
- `image_height`
- `confidence`
- `points.player1_start`
- `points.player1_end`
- `points.player2_start`
- `points.player2_end`

Only these fields are uploaded to the device result object. Classifier,
geometry, engine, and review diagnostics remain in the local `.result.json`
debug artifact so the ESP32 response stays below its receive-buffer limit.
